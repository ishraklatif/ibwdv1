# IBWD v1 — Research Findings & Grounded Implementation Plan

## TL;DR
- A persistent, deterministically-built code knowledge graph is a **validated** pattern: the closest published prior art (Codebase-Memory, arXiv:2603.27277, Mar 2026) reports ~10× fewer tokens, 2.1× fewer tool calls, and sub-millisecond queries while retaining ~90% of a grep-explorer's answer quality — but it wins only on *structural* queries and loses on tasks needing full source lines, so IBWD must be hybrid (graph-first, file-fallback).
- The single biggest correction to the ChatGPT draft: **ship IBWD as an MCP server, not as plain slash commands.** MCP tools are the idiomatic, agent-native integration for Claude Code in 2026; slash commands (now merged into "skills") should be thin wrappers over the MCP tools. SQLite + sqlite-vec is the right v1 storage; Kuzu is now a trap — its GitHub repo was archived on October 10, 2025 (the same day v0.11.3 shipped as a final release), after Apple agreed to acquire Kùzu Inc. on October 9, 2025.
- The proposed Qwen model stack is broadly correct and locally runnable, but names/tags need fixing: `qwen3-coder:30b` (19GB, MoE 3.3B active) for summarization, `qwen3-embedding` (0.6B/4B/8B) for embeddings, and a `dengcao/Qwen3-Reranker` community GGUF for reranking (no first-class official reranker on Ollama yet).

## Key Findings

### 1. Prior art strongly validates the core hypothesis — with important boundaries
The most directly comparable system, **Codebase-Memory** (Vogel et al., arXiv:2603.27277, 28 Mar 2026), is essentially IBWD's structural layer built as an MCP server. Benchmarked across 31 repos (one per language, 78 to 49,398 nodes) with Claude Opus 4.6 as backend, it reports: quality 0.83 (MCP) vs 0.92 (file-explorer) — 90% of explorer quality; 2.3 vs 4.8 tool calls/question (2.1× fewer); ~1,000 vs ~10,000 tokens/question (10× fewer); <1ms vs 10–30s query latency (>100× faster). It wins on hub detection and caller ranking (19/31 languages) and narrows to ~1% gap on functional languages (Haskell, OCaml, Elixir). It loses where the task needs full source context (explorer wins 16/31) or exhaustive grep (10/31), and worst case is macro-heavy C (0.58 vs 1.00) because macros aren't in the AST. The authors' own recommendation, quoted from §5.1: "the optimal architecture is a hybrid: graph-based retrieval for structural queries, with fallback to file exploration for source-level tasks." This is the single most important design lesson for IBWD.

Evidence quality caveat: Codebase-Memory used a single grader (first author), single LLM backend, one repo per language, and ran no head-to-head vs embedding-RAG/LSP/Neo4j. So the numbers are directional, not definitive — which is exactly the gap IBWD's own benchmark can fill. Two mechanistic details worth borrowing: BFS call-path tracing runs in ~0.3ms via a SQL recursive CTE, and fresh indexing is ~6s for 49K nodes / ~3min for the 2.1M-node Linux kernel, with ~1.2s incremental re-index (≈4× faster than full) via XXH3 content hashing.

**Aider repo map** is the canonical tree-sitter + graph-ranking precedent. It parses with tree-sitter (130+ languages via py-tree-sitter-languages / tree-sitter-language-pack), builds a graph of symbol definitions/references, runs **personalized PageRank** (restart vector biased toward files in the current chat), and emits the top-ranked definitions as elided, signature-only views fitted to a token budget via binary search. Key design choices IBWD should borrow: rank symbols by graph centrality (not all symbols are equal — "a function called by 20 other functions is more valuable context than a private helper called once"), show signatures not bodies, respect a token budget, and cache tags to avoid re-parsing unchanged files (mtime-based invalidation). Aider's map is rebuilt in-memory on demand rather than persisted — IBWD's differentiator is persistence + a semantic layer.

**Cursor** indexes by building a **Merkle tree** of file hashes, chunking changed files with tree-sitter, embedding chunks, and storing vectors in a remote store (Turbopuffer), syncing incrementally by walking Merkle diffs. Embeddings are cached by chunk-content hash. The client keeps a fresh regex/trigram index locally because a stale index "sends the agent on a wild goose chase." Lesson for IBWD: content-hash incremental updates are industry standard (validates the SHA256 plan; consider a directory-level Merkle tree), and freshness matters more for exact-match than for semantic recall.

**Continue.dev** does local codebase indexing: embeddings + keyword search, stored locally in `~/.continue/index` using **LanceDB** (embedded), default local embeddings via transformers.js, with **voyage-code-3** recommended as the top hosted code-embedding model. Windsurf's Varun (quoted in LangChain's context-engineering post) gives the key warning: "Indexing code ≠ context retrieval... embedding search becomes unreliable as a retrieval heuristic as the size of the codebase grows." This is a direct argument for IBWD's structural graph traversal on top of embeddings, not embeddings alone.

**Anthropic's own guidance** ("Effective context engineering for AI agents," Sep 29 2025) is the philosophical backbone. Core concepts: context is a finite resource with an "attention budget"; "context rot" degrades recall as tokens grow; the goal is "the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome." Critically for IBWD, Anthropic explicitly describes Claude Code's design as a **hybrid of upfront + just-in-time retrieval**: "CLAUDE.md files are naively dropped into context up front, while primitives like glob and grep allow it to navigate its environment and retrieve files just-in-time, effectively bypassing the issues of stale indexing and complex syntax trees." That last clause is a direct, named skepticism of the exact approach IBWD proposes — IBWD must earn its keep by beating glob/grep on token cost for structural queries, and must treat the graph as a hint that Claude verifies against source, never as ground truth.

### 2. Code parsing & storage: tree-sitter + SQLite is right; avoid Kuzu
Tree-sitter is the de facto standard (used by Aider, Cursor, Continue, GitHub, Neovim, Zed). It's incremental, error-tolerant, and produces a concrete syntax tree that preserves exact byte/line/column positions — ideal for mapping graph nodes back to precise source locations. Trade-off vs Python's `ast`: tree-sitter is a CST (more verbose, syntax-level) while `ast` is a true AST (cleaner semantics but Python-only and harder to map to exact source). Recommendation: use **tree-sitter uniformly** for both Python and JS/TS in v1 for a single consistent pipeline and grammar schema; only reach for Python's `ast` if you need semantic details tree-sitter can't give. Note tree-sitter grammars are LR(1) and macro/preprocessor constructs are invisible to the AST (the Codebase-Memory C weakness).

Heavyweight code-graph precedent (Joern/Code Property Graphs, CodeQL, Sourcegraph SCIP/LSIF, Kythe) confirms the value of structural graphs but also confirms they're overkill: CPGs merge AST+CFG+PDG and need specialized databases and query languages "not designed for LLM consumption." SCIP (Sourcegraph's successor to LSIF) is a good precedent for a portable, protobuf-encoded symbol index if IBWD later wants precise cross-repo "go to definition"; per Meta engineer Don Stewart (@donsbot, May 27 2022), on integrating SCIP into Glean: "The SCIP data is protobuf-encoded and typed, so compared to LSIF its about 8x smaller, and can be processed 3x faster. The mapping into Glean is ~550 loc, vs 1500 for LSIF." For v1, don't adopt these — but their schemas are worth studying.

**Storage: SQLite is the correct v1 choice, now more so than when the ChatGPT draft was written.** Kuzu — the embedded property-graph DB one might have considered — had its GitHub repo archived on **October 10, 2025** (the same day v0.11.3 shipped as a final release, with a note the team was "working on something new"), after **Apple agreed to acquire Kùzu Inc. on October 9, 2025** (surfaced via an EU Digital Markets Act filing in Feb 2026). Maintenance has passed to community forks (LadybugDB and others) — a real supply-chain risk for a foundational dependency. SQLite gives you: nodes/edges tables, recursive CTEs for graph traversal (Codebase-Memory does BFS call-path tracing in ~0.3ms via a SQL recursive CTE), zero server, single-file portability, and a mature vector extension. For vectors, **sqlite-vec** (asg017) is the best fit for a single-developer local tool: vectors live in the same SQLite file, no server, "deploying a new index is copying a file." LanceDB is the strong alternative (embedded, Arrow columnar, disk-based IVF-PQ, used by Continue.dev and AnythingLLM) and is worth adopting only if you outgrow sqlite-vec's scale or want automatic dataset versioning. Avoid ChromaDB for this use case — it runs as a process and has documented HNSW-corruption-on-abrupt-exit issues that pushed at least one code-search MCP project to migrate away.

### 3. Embedding/model stack: mostly right, fix the names
The tiered model idea (deterministic AST → small local LLM for semantics → Claude for final reasoning) is sound and matches the field. Corrections and confirmations on the specific Ollama models (verified against the live Ollama library):

- **Summarizer: `qwen3-coder:30b`** — 30.5B total / 3.3B active MoE, ~19GB at Q4_K_M, 256K context, 4.5M+ pulls. Runs on a 24–32GB GPU or 32GB Mac. This is the right local summarizer. (The 480B tag needs ~250GB — ignore it; a `qwen3-coder-next` 80B-A3B variant also exists.) For lighter machines, alternates include **Devstral** — the original (Mistral AI + All Hands AI, May 2025) scored **46.8% on SWE-Bench Verified** ("outperforming prior open-source SoTA models by more than 6% points"), and the newer **Devstral Small 2 (24B, Dec 2025) now scores 68.0%** and runs on a single RTX 4090 or 32GB Mac — plus `gpt-oss:20b` (16GB RAM).
- **Embeddings: `qwen3-embedding`** — officially on Ollama in 0.6b (639MB), 4b (2.5GB), 8b (4.7GB) sizes, 32K–40K context, ~3.8M pulls. Per the official Qwen blog: "The 8B size embedding model ranks No.1 in the MTEB multilingual leaderboard (as of June 5, 2025, score 70.58)"; it also leads MTEB-Code, is released Apache 2.0 (arXiv:2506.05176), supports 100+ languages incl. programming languages, and offers Matryoshka dimensions (1024/2560/4096 for 0.6B/4B/8B). Excellent and correct choice. For a laptop, start with **`qwen3-embedding:0.6b`** and scale up. Alternatives specifically strong on code: **voyage-code-3** (API, Continue.dev's recommended code model), CodeSage, CodeXEmbed, jina code embeddings. A 2026 code-to-code retrieval benchmark found Qwen3-Embedding and CodeXEmbed dominate Python/Java/C++ near-perfectly, with model-specific weaknesses on harder cross-language sets — so Qwen3-Embedding is a defensible default with voyage-code-3 as a hosted upgrade path.
- **Reranker: no first-class official Ollama reranker yet.** Ollama's `/api/embed` requires GGUF with pooling metadata baked in; reranker support is an open feature request (issues #16076, #10989). In practice people run **`dengcao/Qwen3-Reranker-0.6B`** (community GGUF, sizes 0.6B/4B/8B). So "Qwen3-Reranker on Ollama" is possible but via a community model, not the official library — plan for this friction, or do reranking with the Qwen3-Embedding model's instruction-aware scoring, or defer reranking to a simple graph-distance + vector-score fusion in v1.

### 4. Context engineering, confidence scoring & staleness
The confidence-scored graph idea is well-grounded and matches published practice. Codebase-Memory uses a **6-strategy call-resolution cascade with explicit confidence scores**: import map (0.95), import map suffix (0.85), same module (0.90), unique name (0.75), suffix match (0.55), fuzzy (0.30–0.40); strategies 1–3 resolve ~80% of calls in well-structured codebases (an informal observation, not a measured metric). This validates IBWD's plan to tag edges with confidence + source_type. The broader KG-for-LLM literature confirms: knowledge graphs reduce hallucination by grounding generation in "vetted knowledge" with source traceability (provenance, timestamps, confidence per edge), and multiple papers use exactly IBWD's pattern — a learnable/assigned edge confidence for LLM-inferred edges, plus a "hallucination grader" that discards low-confidence LLM edges (raising precision at the cost of recall, then iterating to recover recall). A clinical-KG audit found LLM-inferred edges averaged 4.84/5 correctness only after post-processing checks removed invalid/low-confidence outputs — i.e., the grader step is load-bearing. Key design implications for IBWD:
- **AST-derived edges: confidence 1.0, source_type=static_analysis. LLM-inferred edges: confidence <1, source_type=llm_inference.** Keep them in separate query paths so Claude can weight authoritative facts over hypotheses. This directly matches confidence-aware KG literature.
- **Never let Claude treat the graph as ground truth.** Anthropic's own note that Claude Code "bypasses issues of stale indexing" via just-in-time grep is the risk to design against. The CLAUDE.md / tool descriptions must instruct verification against actual source.
- **Staleness is the main failure mode of persistent indexes.** Cursor keeps its exact-match index fresh on every edit for this reason; Codebase-Memory uses a file-watcher + XXH3 content hash with ~1.2s incremental re-index (~4× faster than full). Recommendation: adopt content-hashing (SHA256 is fine; XXH3 is faster at ~30GB/s if speed matters) and, ideally, a file-watcher for live sync rather than manual `/graphify` rebuilds. Mark LLM-generated summaries with the content hash they were derived from so they can be invalidated on change.

The "map before territory" pattern is real and endorsed: Anthropic describes progressive disclosure and lightweight identifiers (file paths, stored queries) loaded just-in-time; the LangChain writeup notes graph-based context selection (Aider's PageRank) "outperforms heuristics." But Anthropic's overarching advice is "do the simplest thing that works" and let capable models explore — so IBWD should position itself as an *optional accelerator* for structural queries, measured against the vanilla baseline, not a mandatory layer.

### 5. Claude Code integration: MCP server is the idiomatic path in 2026
This is the biggest correction to the ChatGPT plan. Research strongly supports building IBWD primarily as an **MCP (Model Context Protocol) server** exposing typed tools, with slash commands as optional thin wrappers:
- Every comparable 2025–2026 code-graph project (Codebase-Memory, CodeGraphContext, code-graph-mcp, Code-Graph-RAG, RepoMapper) ships as an **MCP server** exposing structural query tools (e.g. 14 typed tools in Codebase-Memory: indexing/query/analysis/code). MCP is Anthropic's open standard and the "action" layer for Claude Code; skills/commands are the "knowledge" layer. Anthropic's context-engineering post treats MCP tools as first-class context.
- **Slash commands have been merged into "skills"** in current Claude Code. Files in `.claude/commands/*.md` still work (filename = command name; markdown body = prompt; YAML frontmatter supports `description`, `argument-hint`, `allowed-tools` (space-separated, *not* comma-separated!), `model`, `disable-model-invocation`; `$ARGUMENTS` for the whole trailing string or `$1`,`$2` positional; `!\`cmd\`` for inline bash; `@path` for file refs; subdirectories create namespaced commands like `/project:frontend:component`). But the recommended pattern is now `.claude/skills/<name>/SKILL.md` (model-invoked by description match) for capabilities and MCP tools for actions.
- There is a known **collision bug** where custom slash commands and MCP servers can conflict on tool-name uniqueness (issue #703, "Tool names must be unique") — another reason to make MCP the primary surface and keep slash commands minimal.

**Recommended IBWD integration:**
1. Primary: an **IBWD MCP server** (Python; Anthropic ships an official Python MCP SDK) exposing tools like `ibwd_search(query)`, `ibwd_impact(symbol)`, `ibwd_graph(topic)`, `ibwd_callers(symbol)`, `ibwd_dependents(symbol)`, `ibwd_tests_for(symbol)`, `ibwd_scan()`. Each tool returns token-efficient, structured results with confidence + source_type + exact file:line so Claude can jump to source. Follow Anthropic's tool-design guidance: self-contained, minimal-overlap, token-efficient, unambiguous ("If a human engineer can't definitively say which tool should be used, an AI agent can't be expected to do better").
2. Secondary/UX: thin slash commands (`/graphify`, `/graph`, `/impact`) in `.claude/commands/` that simply invoke the MCP tools, for ergonomic manual triggering.
3. CLAUDE.md: short (community rule of thumb: keep it ≤~200 lines), instructing Claude to prefer IBWD structural tools for impact/dependency/architecture questions, fall back to glob/grep for full-source/exhaustive-text tasks, and always verify graph claims against source before editing.

### Data / graph schema (informed by Codebase-Memory & CPG)
Node types: Project, Package, Folder, File, Module, Class, Function, Method, Interface/Type, plus semantic nodes (Summary, Responsibility, Component/ADR) and historical nodes (Commit, PR). Edge types: CONTAINS, DEFINES, IMPORTS, CALLS, INHERITS, IMPLEMENTS, DECORATES (structural, confidence 1.0), plus RELATES_TO / RESPONSIBLE_FOR / SIMILAR_TO (semantic, confidence <1, source_type=llm_inference), plus TESTS and TOUCHED_BY (historical). Every node stores exact file:line and the content hash it was derived from; every edge stores confidence + source_type. This makes edges invalidatable on file change and lets Claude filter by authority.

### Phased build milestones mapped to Claude Code tasks
The 7-phase plan is sound; reorder slightly so the MCP interface and evaluation harness appear earlier:
1. **Repo scanner + SQLite schema + manifest** — file nodes, content hashing, ignore rules. (Claude Code task: scaffold `src/ibwd/{cli,scanner,graph}`, SQLite DDL, hash-based change detection.)
2. **tree-sitter structural extraction (Py + JS/TS)** — classes/functions/imports/calls/inheritance as confidence-1.0 edges with file:line. (Task: grammar loading, `.scm` tag queries adapted from Aider (Apache-2.0), call/def resolution with a confidence cascade.)
3. **Git integration + incremental hashing** — only reprocess changed files; historical nodes (commits/PRs) optional. (Task: GitPython wrapper, XXH3/SHA256 diffing.)
4. **Embeddings + semantic search + graph traversal + MCP server (MVP)** — embed entities via `qwen3-embedding`, store in sqlite-vec, expose `ibwd_search`/`ibwd_impact`/`ibwd_callers` over MCP. Traversal via recursive CTEs. Ship the MCP server here so you can dogfood early. (Task: embedding pipeline, vector index, MCP tool definitions per Anthropic tool-design guidance.)
5. **Local AI summarization layer** — `qwen3-coder:30b` generates file/class/function summaries + responsibility/intent, tagged confidence<1 + source_type=llm_inference + source content-hash. (Task: Ollama client, prompt templates, hallucination-grader step that drops low-confidence inferred edges.)
6. **Ranking/reranking + context builder** — PageRank-style centrality (borrow Aider) + vector score + graph distance; token-budgeted, signature-only context assembly with binary-search fitting. (Task: networkx PageRank, fusion scorer, token budgeter.)
7. **CLAUDE.md + slash-command wrappers + benchmark harness** — thin `/graphify` `/graph` `/impact`; CLAUDE.md verification instructions; full eval vs vanilla baseline. (Task: `.claude/commands/*.md`, CLAUDE.md, benchmark scripts.)

### Repo layout (keep, minor additions)
`ibwd/` with `src/ibwd/{cli.py, scanner/, graph/, ai/, git/, mcp/, retrieval/}`, `.claude/commands/`, `CLAUDE.md`, `tests/`, and `benchmarks/`. Add `mcp/` (server + tool defs) and `retrieval/` (ranking + context builder) as first-class packages.

### Evaluation / benchmarking plan (make this rigorous — it's the whole thesis)
Adopt Codebase-Memory's metrics but fix its weaknesses (single grader, one repo/language, no strong baselines):
- **Baselines:** (a) vanilla Claude Code with glob/grep/read only; (b) embedding-only RAG (no graph); (c) IBWD full (graph + embeddings + rerank). Comparing against (b) is what Codebase-Memory omitted and what will prove the graph adds value beyond embeddings.
- **Metrics per task:** input/output tokens, tool calls, files read, wall-clock latency, retrieval precision/recall (vs a hand-labeled relevant-set), and task success rate (tests pass / correct answer).
- **Task taxonomy split by type** (the key insight from prior art): separate *structural* tasks (impact analysis, "what calls X", dependency chains, "where is Y implemented") from *source-level* tasks (full-file understanding, exhaustive text search). Expect IBWD to win big on the former and roughly tie/lose on the latter — report them separately rather than as one blended number.
- **Multiple repos, multiple graders, multiple LLM backends** if feasible; at minimum blind grading and >1 repo per language.
- **Success threshold that would change the recommendation:** if IBWD can't beat glob/grep on tokens for structural tasks by a clear margin (Codebase-Memory saw ~10×) while staying within ~5–10% of baseline task success, the persistent graph isn't earning its complexity and you should fall back to Aider-style on-demand repo maps.

## Recommendations
1. **Build the structural graph first and prove it in isolation.** Phases 1–4 give you a deterministic tree-sitter → SQLite graph exposed via MCP with `ibwd_impact`/`ibwd_callers`. Benchmark this alone against glob/grep on *structural* tasks before adding any LLM semantics. Threshold to proceed: ≥5× token reduction on structural tasks at ≥90% of baseline success.
2. **Make MCP the primary interface, slash commands a thin convenience layer, CLAUDE.md the guardrail.** This is the idiomatic 2026 Claude Code integration and avoids the slash-command/MCP collision bug.
3. **Keep the two-tier confidence model strict.** AST edges = 1.0/static_analysis; LLM edges = <1/llm_inference, in separate query paths, each stamped with the source content-hash. Add a hallucination-grader pass that drops low-confidence inferred edges (the clinical-KG and event-graph literature shows this is what makes LLM edges trustworthy). Never present the graph to Claude as ground truth — instruct verification against source in CLAUDE.md and in every tool's result schema.
4. **Fix the model tags now:** `qwen3-coder:30b`, `qwen3-embedding:0.6b` (scale to 4b/8b on capable hardware), `dengcao/Qwen3-Reranker-0.6B` or defer reranking. Keep an OpenAI-compatible seam so voyage-code-3 (or Devstral Small 2 for a stronger local summarizer) can be swapped in.
5. **Design for freshness from day one.** Content-hash incremental updates + an optional file-watcher for live sync; invalidate summaries/embeddings by source hash. Staleness is the documented failure mode of every persistent code index.
6. **Defer aggressively:** no Neo4j (SQLite CTEs suffice), no Kuzu (archived), no multi-agent, no 20+ languages, no autonomous modification, no fine-tuning. If you outgrow sqlite-vec, migrate to LanceDB; if you need precise cross-repo nav, study SCIP.
7. **Split every benchmark by task type** (structural vs source-level) and include an embedding-only baseline — that's how you turn a demo into a defensible master's-thesis result.

## Caveats
- The headline Codebase-Memory numbers (10× tokens, 83% vs 92% quality) come from a single-author-graded, single-backend (Claude Opus 4.6), one-repo-per-language study with no comparison to embedding-RAG or LSP; treat them as directional evidence, not proof. Your own benchmark is what will make IBWD's claim rigorous.
- Anthropic's stated position is that Claude Code's glob/grep + CLAUDE.md hybrid deliberately "bypasses issues of stale indexing and complex syntax trees," and that the field trends toward letting capable models explore with less scaffolding. IBWD is swimming slightly against that current; it must justify itself on measured token/latency wins for structural queries, not on principle.
- Structural graphs cannot represent runtime behavior, reflection, dynamic dispatch, or macros/preprocessor constructs (the documented C weakness, 0.58 vs 1.00). Scope claims to static structure.
- LLM-inferred semantic edges carry genuine hallucination risk; the confidence tiering + grader mitigates but does not eliminate it. Audit a sample of inferred edges periodically.
- Model/tooling availability is a moving target (the Ollama library, Claude Code skills/commands, and the MCP spec all shipped changes through 2026); re-verify exact tags and the current commands-vs-skills guidance at build time.
- Some sourcing here is secondary (blog posts, vendor pages) rather than primary; the Anthropic engineering posts, the arXiv papers, the Qwen blog/paper, and the official Ollama/Claude Code docs are the load-bearing citations.
